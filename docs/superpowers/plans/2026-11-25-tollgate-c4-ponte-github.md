# tollgate C4a: fondamenta del ponte con GitHub

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** La prima delle due parti di C4 (scelta dell'utente del 25/11/2026). C4a costruisce il **trasporto** verso GitHub, senza ancora le bacheche: il token delle bacheche in un file protetto che solo il codice di tollgate legge; `gh api graphql` con le variabili come dato, la redazione dei messaggi d'errore e le classi d'errore; le operazioni verso GitHub, ognuna con la sua strategia contro i doppioni; la coda delle scritture nello stato locale (migrazione 8, attesa crescente, abbandono, evento `sync`), svuotata da un processo staccato che non fa mai aspettare il lavoro; il filtro di ciò che esce (lista «non va mai» del progetto 7) con il test dei canarini; il campo `queue` della fotografia; una sonda su GitHub vero, fatta dal controller sul repo di prova privato dell'utente, che raccoglie anche i fatti che serviranno a C4b. Il contenuto (bacheca principale, bacheca di progetto, macchina che possiede un lavoro, avvisi, allineamento) è di **C4b**, con un piano scritto dopo la sonda.

**Architecture:** Cinque moduli nuovi, negli strati che `tests/test_layers.py` ammette. `tollgate_core/ghcli.py` (esteso, senza stato, usato anche dal gate): `Secret`, `redact`, `Reply`, `classify`, `call`, `graphql`, `rest`. `tollgate_core/boardtoken.py`: il file del token (percorso, controllo dei permessi, lettura, scrittura, rimozione). `tollgate_core/ghops.py`: le operazioni (`OPS`), una sola prova per chiamata, con il controllo prima della scrittura dove serve. `tollgate_analysis/outbound.py`: il filtro puro (tipi dei campi per ogni tipo di voce, divieti su ogni stringa, forma di `repo_key`). `tollgate_core/ghqueue.py`: la tabella `gh_queue` e l'unico ingresso `submit`. `tollgate_core/ghdrain.py`: lo svuotamento (lucchetto, budget, ordine per lavoro, attese, blocchi) e l'avvio staccato (`kick`). I comandi stanno sotto `tollgate board …` (`tollgate_core/board_cli.py`); gli hook e la CLI chiamano solo `kick`, che non parla mai con GitHub.

**Tech Stack:** Python ≥ 3.11, solo libreria standard (`sqlite3`, `fcntl`, `getpass`, `os.fork`); bash; `gh` 2.46.0 (solo nella sonda, dal controller); `unittest` con `tests/run` (python3.11 e python3) e `tests/fakegh.py` come `gh`.

**Spec:** il progetto di C `docs/superpowers/specs/2026-11-20-tollgate-c-tracciamento-design.md`, sezioni 4, 7 e 8 (l'autorità), poi 2, 3, 5, 6, 9, 10, 12, 13, 14; il piano principale di C `docs/superpowers/plans/2026-11-20-tollgate-c-piano-principale.md` (regole 1-6, riga C4 della sezione 2, sezione 3, sezione 6, decisioni 2, 3 e 5, sezione 8); la spec del nucleo `docs/superpowers/specs/2026-10-08-tollgate-nucleo-design.md`, revisione 37 (3.1, 7.2, 7.4, 11.2, 11.3, 11.4, 12.2, 16, 18.4, 20). Le scelte dell'utente del 25/11/2026 (C4 in due parti, token in un file protetto) si scrivono nel progetto di C dal Task 11. La revisione 38 della spec la scrive il Task 11.

## Global Constraints

- Solo libreria standard in `bin/` e nei test; Python ≥ 3.11. Ogni task chiude con `tests/run` verde (`python3.11` e `python3`); verifica finale come la CI: `PYTHONWARNINGS=error::ResourceWarning tests/run`, nessun «unclosed database». I file nuovi si aggiungono a git **prima** della suite (`tests/test_b1_scripts.py` copia il plugin dai soli file tracciati). Nessun `__pycache__` (`-B`).
- **Strati** (`tests/test_layers.py`, `tests/test_analysis_isolation.py`): `tollgate_analysis.outbound` non importa nulla di tollgate fuori da `tollgate_analysis`; i moduli nuovi di `tollgate_core` non importano `tollgate_flow`, `tollgate_hooks`, `tollgate_checks`, `tollgate_gate`; `ghcli` resta senza stato e senza `sqlite3` (lo usa il gate) e non importa i moduli nuovi.
- **Nessun modello di linguaggio nel codice.** Solo il codice di tollgate scrive su GitHub; il modello non ha comandi nuovi per farlo (i `board` sono del coordinatore e due richiedono un terminale). Nessun workflow di GitHub Actions per le bacheche.
- **Niente GitHub vero** nei test, nei subagenti e negli script tranne la sonda (Task 4, solo il controller, ogni `gh` passato dal profilo `c4` della guardia) e il push di `main` dalla guardia `p5`. Il `gh` dei test è `tests/fakegh.py` via `TOLLGATE_GH`. Nessun `claude -p`, nessun eval.
- **Il valore di un token non si legge, non si stampa e non si scrive mai** in un file del repo, in un log, in un messaggio, nello stato, in un argomento di un processo. Lo legge solo `boardtoken.read`, all'inizio di ogni svuotamento o comando `board`, lo tiene solo in un `ghcli.Secret` e lo passa solo come `GH_TOKEN` nell'ambiente del figlio. Di una variabile d'ambiente si può sapere solo se è impostata. Nei test il token delle bacheche vale `PROVA-123`; una stringa con la **forma** di un token di GitHub si costruisce per concatenazione (`"gh" + "p_" + "A" * 36`), mai come letterale in un file.
- Testo non fidato (titoli, corpi) mai in un argomento di `gh`: sempre in un file `--input` (JSON) creato 0600 in una cartella 0700 e cancellato dopo la chiamata.
- **Cosa non cambia:** il gate (`bin/tollgate_gate/`) salvo ciò che eredita da `ghcli` (messaggi d'errore redatti); `apply._OPS`; le skill, i profili, i frammenti e le pagine approvate (`skills/rules-*`, `templates/profiles/*`, `docs/profili/*`); `templates/tollgate.toml`; la busta degli eventi (`v` 1) e la fotografia (`v` 1).
- Il repo è pubblico: niente nome utente della macchina, host, nomi di progetti privati, token; nel rapporto della sonda niente nomi né identificativi dell'account. Identificatori in inglese, testi in italiano.

## Decisioni di questo piano

Ogni decisione ha il costo se sbagliata. Le scelte «utente» non si discutono. Il Task 11 le riporta nella revisione 38.

1. **C4 in due parti (utente, 25/11/2026).** Questo piano è C4a: trasporto, coda, filtro, token, sonda. C4b (bacheche, macchina che possiede un lavoro, eventi mostrabili, avvisi, allineamento) ha un piano scritto dopo la sonda, dal codice reale di C4a (regola 1 del piano principale). I file di C4a tengono il nome `…-c4-…`; quelli di C4b saranno `…-c4b-…`. Costo accettato dall'utente: una sessione di scrittura, una d'esecuzione e un merge in più, circa il 20-30% di abbonamento in più; nessuna spesa in denaro.
2. **Forma del token: classico, con il solo scope `project`** (piano principale, decisione 3). I token a grana fine non danno i Projects di un utente (fatto). Il token delle bacheche serve solo alle chiamate GraphQL dei Projects (`client = "board"`); issue, sotto-issue, dipendenze, assegnazioni, commenti e conteggi passano dal `gh` già autenticato dell'agente (`client = "agent"`). Se la sonda mostra che il solo `project` non basta ad aggiungere a una bacheca un'issue di un repo privato: fermata `scope repo` («La sonda»). Costo: due credenziali da tenere in vita; un'operazione sul client sbagliato fallisce con `auth` o `rejected` (test `test_ops_use_declared_client`).
3. **Dove sta il token (utente, 25/11/2026: file protetto).** `~/.config/tollgate/board-token` (`boardtoken.token_path`), cartella 0700, file 0600. Percorso fisso come la cartella di stato (`paths.default_state_root` ignora `XDG_*`), così una variabile dell'ambiente del modello non lo sposta (cambio rispetto alla proposta del controller con `XDG_CONFIG_HOME`). Mai nella cartella di stato: le evidenze degli eval ne contengono copie (C1, Task 8). `boardtoken.status` rifiuta, guardando solo `lstat` e mai il contenuto, un link simbolico, un file non regolare, di un altro utente, con permessi oltre 0600, o una cartella scrivibile da gruppo o altri: stato `unsafe` con il motivo (`symlink`, `not_file`, `owner`, `mode`, `dir_mode`). In test il percorso è `TOLLGATE_BOARD_TOKEN_FILE` (nuova in `TEST_ENVS`). Costo: un utente che tiene i segreti altrove deve usare questo percorso; con `HOME` condivisa tra macchine (raro) il token è lo stesso.
4. **Comandi del token**: `tollgate board token set` legge con `getpass.getpass` e **rifiuta se `sys.stdin.isatty()` è falso** (niente pipe, argomento, cronologia della shell; il modello non ha un terminale); rifiuta un valore vuoto, con spazi, oltre 255 caratteri o che comincia con `github_pat_` (grana fine), avvisa se non comincia con `ghp_`; scrive con `O_CREAT|O_EXCL|O_NOFOLLOW` 0600 su un file temporaneo e `os.replace`; cancella il blocco `gh_block`. `board token status` stampa una riga: `token delle bacheche: presente`, `token delle bacheche: assente`, `token delle bacheche: non sicuro (<motivo>)`; uscita 0, 1, 1. `board token check` (rete, esplicito) chiama `gh api --include rate_limit` con il token e stampa `scope del token: <elenco>` da `X-OAuth-Scopes`; avvisa `il token ha scope in più (<elenco>): basta project` e esce 1 se manca `project`. `board token remove` chiede conferma (`sì`) da un terminale, cancella il file e il blocco. `board` entra in `_COORDINATOR_ONLY`. Costo: chi usa tollgate senza terminale interattivo non può impostare il token.
5. **`/tollgate:setup`**: un passo nuovo (5) che lancia `<programma> board token status` (l'unico comando che la skill esegue: la frase finale diventa «Non eseguire altri comandi oltre a `board token status`») e, se il token manca o non è sicuro, mostra i passi: token classico con il solo `project` e una scadenza, `board token set` in un terminale a parte, mai incollarlo nella chat (se succede: revocarlo e rifarlo). Il setup non blocca. Costo: un passo in più nella skill; `test_skill_contract` controlla che il comando esista.
6. **Spento (progetto 8).** `[board] enabled = true` per difetto, unica chiave di `[board]` in C4a. Senza token, con un token non sicuro o con `enabled = false` nel repo, `ghqueue.submit` non mette niente in coda e non registra niente: tollgate funziona come oggi. Predefinito `true` perché senza token è comunque spento. **Cambio rispetto al controller:** la fotografia è della macchina, non di un repo, quindi `queue.state = "off"` ha i motivi `no_token` e `unsafe_token`, non `disabled` (la configurazione è per repo e la fotografia non la legge). Le voci già in coda di un repo spento partono lo stesso. Costo: l'utente che spegne un repo vede le ultime voci uscire; per fermare tutto c'è `board token remove`.
7. **Il token nel processo e la redazione.** `ghcli.Secret` (`__slots__`, `repr` e `str` danno `Secret(***)`, `reveal()` solo per l'ambiente del figlio). Con `token` dato, `ghcli.run` toglie dall'ambiente ereditato `TOKEN_ENV_DROP = ("GH_TOKEN", "GITHUB_TOKEN", "GH_ENTERPRISE_TOKEN", "GITHUB_ENTERPRISE_TOKEN", "GH_HOST", "GH_DEBUG", "DEBUG")` e mette `GH_TOKEN`; senza token l'ambiente resta com'è oggi (il gate su Actions ne ha bisogno). `GH_HOST` esce perché il token vada solo a github.com, `GH_DEBUG` perché `gh` registrerebbe il traffico. `ghcli.redact(text, secrets=())` sostituisce con `[token]` i valori dei segreti e ogni forma `gh[pousr]_…` e `github_pat_…`; `_failed` e ogni messaggio di `call` passano da lì, anche per le chiamate dell'agente e del gate. Nella coda e negli eventi **non si salva mai il testo d'un errore**: solo la classe. Costo: un messaggio d'errore con una parola lunga di quella forma diventa illeggibile in quel punto.
8. **Errori di `gh`.** `ghcli.call(state, args, *, token=None, timeout=GH_TIMEOUT_S) -> Reply` fa **una sola prova**, sempre con `--include`, con `cwd = state.root`, e non solleva per un errore HTTP. `Reply(status, headers, data, errors, error_class, retry_after_s)`. `classify` in quest'ordine: uscita 0, stato < 400 e nessun `errors` → `None`; stato 401 o uscita 4 → `auth`; stato 403 o 429 con `retry-after` o `x-ratelimit-remaining: 0`, oppure 200 con `errors` e `x-ratelimit-remaining: 0`, oppure un errore che contiene `secondary rate limit` → `rate_limit`; stato ≥ 500, timeout, `gh` mancante, o stderr che corrisponde a `_TRANSIENT` senza stato → `transient`; il resto → `rejected`. `retry_after_s` = `retry-after`, altrimenti `x-ratelimit-reset` meno l'ora, altrimenti 60, mai sotto `RATE_LIMIT_MIN_S = 60`. Le funzioni esistenti (`run_json`, `api`) non cambiano comportamento. Costo: un errore che GitHub dà in una forma diversa finisce in `rejected` e consuma tentativi; la sonda (S15) e il Task 5 allineano le forme.
9. **GraphQL con `--input`.** `ghcli.graphql(state, query, variables, *, token, tmpdir, timeout) -> Reply` scrive `{"query": …, "variables": …}` in un file e lancia `gh api --method POST --include --input <file> graphql`; `ghcli.rest(state, method, path, *, body=None, token=None, tmpdir, timeout) -> Reply` fa lo stesso per REST (corpo JSON in `--input`). Il testo della query è costante del codice; ogni dato è una variabile. `tmpdir` è `<stato>/tmp`, creata 0700; ogni file è 0600 e si cancella nel `finally` della chiamata. Se la sonda (S20) mostra che gh 2.46 non accetta il corpo GraphQL con `--input`: fermata `fatto diverso`, con la strada di riserva `-F query=@file` più `-F nome=@file` per le stringhe. Costo: un file temporaneo per chiamata.
10. **Il modello non apre il file del token (utente, 25/11/2026), forma minima.** (a) La cartella del token entra in `Ctx.protected_roots`: `Edit`, `Write`, `MultiEdit`, `NotebookEdit` e le scritture da Bash sono negate dai controlli esistenti. (b) Un controllo nuovo `bin/tollgate_checks/token_file.py` (eventi `pre_read` e `pre_bash`, ordine 5) nega un `Read` o un `Grep` il cui percorso, in ogni sua forma (`path_forms`), è la cartella del token o sta dentro, e un comando Bash che corrisponde a `TOKEN_MENTION = r"\.config/tollgate|tollgate/board-token"` dopo l'espansione di `~`, `$HOME` e `${HOME}`. (c) Il matcher di `PreToolUse` prende anche `Read|Grep`; il wrapper esce subito con 0 per `Read` e `Grep` se `file_path` e `path` non contengono `.config/tollgate`, così Python parte solo in quel caso; `pre_read` è un evento di controllo. Limiti scritti nella pagina d'uso: vale solo dove tollgate è attivo (il wrapper esce prima in un repo non attivo, o con `OFF`), e un comando offuscato non si riconosce; resta la protezione dei permessi del file. Costo: un `git commit -m` o un `grep` che nomina quel percorso è negato anche nello sviluppo di tollgate (si riformula).
11. **La coda: tabella `gh_queue`, migrazione 8.** Non si riusa `intents` (ciclo di vita legato a un lavoro e agli atti; costo di riusarla: stati e chiavi da piegare). Colonne: `id INTEGER PRIMARY KEY AUTOINCREMENT`, `kind TEXT NOT NULL`, `key TEXT NOT NULL UNIQUE`, `repo_key TEXT NOT NULL`, `issue INTEGER`, `work INTEGER`, `payload TEXT NOT NULL` (JSON già filtrato), `rev INTEGER NOT NULL DEFAULT 1`, `state TEXT NOT NULL CHECK (state IN ('pending','done','abandoned'))`, `attempts INTEGER NOT NULL DEFAULT 0`, `next_at TEXT NOT NULL`, `error_class TEXT CHECK (error_class IS NULL OR error_class IN ('transient','rate_limit','auth','rejected'))`, `result TEXT` (JSON: numeri e id di nodo restituiti da GitHub, mai testo), `created_at TEXT NOT NULL`, `updated_at TEXT NOT NULL`; indice `gh_queue_due ON gh_queue(state, next_at)`. Nessun `CHECK` su `kind` (C4b e C5 ne aggiungono senza migrazione: il controllo è `outbound.KINDS`). `rev` cresce a ogni sostituzione del payload: `ghqueue.mark_done(conn, id, rev, result, *, now)` chiude la voce solo se `rev` è quello letto, altrimenti resta `pending` (una sostituzione durante lo svuotamento non si perde). Costo: una tabella in più nello stato; una riga per chiave per sempre (una chiave = una cosa su GitHub).
12. **Chiave e sostituzione per tipo.** `ghqueue.item_key(kind, repo_key, issue, payload) -> str` = `kind|repo_key|issue o 0|` seguito dai valori dei `key_fields` del tipo, uniti da `|`. Ogni tipo dichiara `upsert`: `replace` (vale l'ultimo stato: `draft`, `field_value`, `assign`, `unassign`) sostituisce il payload di una voce `pending`, rimette in `pending` una voce `done` o `abandoned` con `attempts = 0`; `keep` (creazioni: `project`, `field`, `item`, `issue`, `sub_issue`, `blocked_by`, `comment`) non fa niente se la chiave esiste in qualunque stato. Le voci dello stesso lavoro (`repo_key`, `issue`; `issue` nullo è il gruppo del repo) si eseguono in ordine di `id`: la prima voce `pending` di un gruppo non scaduta o fallita ferma le altre del gruppo, non gli altri gruppi. Costo: una creazione abbandonata non si rifà da sola (serve `board retry`).
13. **Attesa crescente e abbandono.** `ghqueue.RETRY_DELAYS_S = (60, 300, 1800, 7200, 21600, 86400)` (l'ultimo vale per ogni tentativo dopo il sesto), `ghqueue.MAX_ATTEMPTS = 8`. Le attese sommano circa 2 giorni e 8 ore di macchina accesa (**correzione del conto del controller**, che diceva 3 giorni e mezzo: sette attese, 203.760 s); un tentativo conta solo quando gira davvero. All'ottavo fallimento `transient` o `rejected` la voce diventa `abandoned`, nasce `sync` con `outcome = "abandoned"`, la fotografia la conta, l'avvio di sessione lo dice in una riga, `board retry` la rimette in attesa. Costo: un guasto lungo di GitHub con la macchina sempre accesa fa abbandonare voci che poi vanno rimesse a mano.
14. **Limiti di frequenza e accesso negato: il blocco.** Il blocco sta in `meta`, chiave `ghdrain.BLOCK_KEY = "gh_block"`, valore JSON `{"reason": "rate_limit"|"auth", "until": <ISO>|null, "strikes": <n>}`. `rate_limit` ferma tutto lo svuotamento fino a `until` = ora + `max(retry_after_s, RATE_LIMIT_MIN_S * 2 ** (strikes - 1))`, al più `RATE_LIMIT_MAX_S = 3600`, senza contare un tentativo; un successo azzera `strikes`. `auth` ferma tutto senza scadenza e senza contare tentativi: lo tolgono `board token set`, `board token remove` e un `board sync` che riesce. Costo: un `auth` dato per sbaglio da GitHub ferma la coda finché l'utente non lancia `board sync`.
15. **Le scritture non idempotenti** (tabella «Le scritture verso GitHub»): si ripetono senza controllo solo le operazioni che GitHub rende idempotenti o che impostano uno stato; le creazioni si **ricontrollano prima**, cercando un marcatore stabile e non delicato, `ghops.marker(key) = "<!-- tollgate:" + kind + ":" + sha256(key)[:16] + " -->"`, aggiunto dall'operazione in fondo al corpo dopo la normalizzazione (un testo dell'utente non può imitarlo: `defuse`); sotto-issue, dipendenze e assegnazioni si leggono prima. Ogni operazione comincia sempre dal controllo, quindi dopo un 500 a corpo vuoto il tentativo successivo riparte da lì. Costo: una lettura in più per ogni creazione; una creazione riuscita che GitHub non mostra ancora nella lettura (S22) darebbe un doppione.
16. **Payload per nomi, non per id.** Un payload nomina il progetto per titolo, il campo per nome, l'issue per numero: l'operazione trova gli id con le letture, che `ghops.Clients.cache` tiene per la durata di uno svuotamento.
