# tollgate C4a: fondamenta del ponte con GitHub

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** La prima delle due parti di C4 (scelta dell'utente del 25/11/2026). C4a costruisce il **trasporto** verso GitHub, senza ancora le bacheche: il token delle bacheche in un file protetto, che legge solo il codice di tollgate e che il modello non può leggere chiamandolo per nome (decisione 10: non è una cassaforte); `gh api graphql` con le variabili come dato, la redazione dei messaggi d'errore e le classi d'errore; le operazioni verso GitHub, ognuna con la sua strategia contro i doppioni; la coda delle scritture nello stato locale (migrazione 8, attesa crescente, abbandono, evento `sync`), svuotata da un processo staccato che non fa mai aspettare il lavoro; il filtro di ciò che esce (lista «non va mai» del progetto 7) con il test dei canarini; il campo `queue` della fotografia; una sonda su GitHub vero, fatta dal controller sul repo di prova privato dell'utente, che raccoglie anche i fatti che serviranno a C4b. Il contenuto (bacheca principale, bacheca di progetto, macchina che possiede un lavoro, avvisi, allineamento) è di **C4b**, con un piano scritto dopo la sonda.

**Architecture:** Otto file nuovi in `bin/` più `ghcli` esteso, negli strati che `tests/test_layers.py` ammette. `tollgate_core/ghcli.py` (esteso, senza stato, usato anche dal gate): `Secret`, `redact`, `Reply`, `classify`, `call`, `graphql`, `rest`. `tollgate_core/boardtoken.py`: il file del token (percorso, controlli, lettura, scrittura, rimozione). `tollgate_core/ghqueries.py`: l'**unica fonte** dei documenti GraphQL e delle chiamate REST, usata dalle operazioni, dalla sonda, dalla guardia e da `fakegh`. `tollgate_core/ghops.py`: le operazioni (`OPS`), una sola prova per chiamata, con il controllo prima della scrittura dove serve. `tollgate_analysis/outbound.py`: i tipi di voce (`KINDS`) e il filtro puro (campi, divieti su ogni stringa, forma di `repo_key`). `tollgate_core/ghqueue.py`: la tabella `gh_queue`, il blocco e l'unico ingresso `submit`. `tollgate_core/ghdrain.py`: lo svuotamento (lucchetto, budget, ordine per lavoro, attese, blocchi) e l'avvio staccato (`kick`). `tollgate_checks/token_file.py`: il blocco delle letture che nominano il file del token. I comandi stanno sotto `tollgate board …` (`tollgate_core/board_cli.py`); solo la fine di un hook chiama `kick`, che non parla mai con GitHub.

**Tech Stack:** Python ≥ 3.11, solo libreria standard (`sqlite3`, `fcntl`, `getpass`, `os.fork`); bash; `gh` 2.46.0 (solo nella sonda, dal controller); `unittest` con `tests/run` (python3.11 e python3) e `tests/fakegh.py` come `gh`.

**Spec:** il progetto di C `docs/superpowers/specs/2026-11-20-tollgate-c-tracciamento-design.md`, sezioni 4, 7 e 8 (l'autorità), poi 2, 3, 5, 6, 9, 10, 12, 13, 14; il piano principale di C `docs/superpowers/plans/2026-11-20-tollgate-c-piano-principale.md` (regole 1-6, riga C4 della sezione 2, sezione 3, sezione 6, decisioni 2, 3 e 5, sezione 8); la spec del nucleo `docs/superpowers/specs/2026-10-08-tollgate-nucleo-design.md`, revisione 37 (3.1, 7.2, 7.4, 11.2, 11.3, 11.4, 12.2, 16, 18.4, 20). Le scelte dell'utente del 25/11/2026 (C4 in due parti, token in un file protetto) si scrivono nel progetto di C dal Task 11. La revisione 38 della spec la scrive il Task 11.

## Global Constraints

- Solo libreria standard in `bin/` e nei test; Python ≥ 3.11. Ogni task chiude con `tests/run` verde (`python3.11` e `python3`); verifica finale come la CI: `PYTHONWARNINGS=error::ResourceWarning tests/run`, nessun «unclosed database». I file nuovi si aggiungono a git **prima** della suite (`tests/test_b1_scripts.py` copia il plugin dai soli file tracciati). Nessun `__pycache__` (`-B`).
- **Strati** (`tests/test_layers.py`, `tests/test_analysis_isolation.py`): `tollgate_analysis.outbound` non importa nulla di tollgate fuori da `tollgate_analysis`; i moduli nuovi di `tollgate_core` non importano `tollgate_flow`, `tollgate_hooks`, `tollgate_checks`, `tollgate_gate`; `ghcli` resta senza stato e senza `sqlite3` (lo usa il gate) e non importa i moduli nuovi.
- **Nessun modello di linguaggio nel codice.** Solo il codice di tollgate scrive su GitHub; il modello non ha comandi nuovi per farlo (i `board` sono del coordinatore e due richiedono un terminale). Nessun workflow di GitHub Actions per le bacheche.
- **Niente GitHub vero** nei test, nei subagenti e negli script tranne la sonda (Task 4, solo il controller, ogni `gh` passato dal profilo `c4` della guardia) e il push di `main` dalla guardia `p5`. Il `gh` dei test è `tests/fakegh.py` via `TOLLGATE_GH`. Nessun `claude -p`, nessun eval.
- **Il valore di un token non si legge, non si stampa e non si scrive mai** in un file del repo, in un log, in un messaggio, nello stato, in un argomento di un processo. Lo legge solo `boardtoken.read`, all'inizio di ogni svuotamento o comando `board`, lo tiene solo in un `ghcli.Secret` e lo passa solo come `GH_TOKEN` nell'ambiente del figlio. Di una variabile d'ambiente si può sapere solo se è impostata. Nei test il token delle bacheche vale `PROVA-123`; una stringa con la **forma** di un token di GitHub si costruisce per concatenazione (`"gh" + "p_" + "A" * 36`), mai come letterale in un file.
- **La suite non tocca mai il file vero del token.** In modo di test il token esiste solo in `TOLLGATE_BOARD_TOKEN_FILE`; senza la variabile è «assente», e una scrittura o una cancellazione del percorso vero (in ogni sua forma) è rifiutata anche se la variabile lo nomina (decisione 3, `test_test_mode_never_uses_real_path`). Nessun test, subagente o script legge `~/.config/tollgate/`.
- Testo non fidato (titoli, corpi) mai in un argomento di `gh`: sempre in un file `--input` (JSON) creato 0600 in una cartella 0700 e cancellato dopo la chiamata.
- **Cosa non cambia:** il gate (`bin/tollgate_gate/`) salvo ciò che eredita da `ghcli` (messaggi d'errore redatti); `apply._OPS`; le skill, i profili, i frammenti e le pagine approvate (`skills/rules-*`, `templates/profiles/*`, `docs/profili/*`); `templates/tollgate.toml`; la busta degli eventi (`v` 1) e la fotografia (`v` 1).

## Decisioni di questo piano

Ogni decisione ha il costo se sbagliata. Le scelte «utente» non si discutono. Il Task 11 le riporta nella revisione 38.

1. **C4 in due parti (utente, 25/11/2026).** Questo piano è C4a: trasporto, coda, filtro, token, sonda. C4b (bacheche, macchina che possiede un lavoro, eventi mostrabili, avvisi, allineamento) ha un piano scritto dopo la sonda, dal codice reale di C4a (regola 1 del piano principale). I file di C4a tengono il nome `…-c4-…`; quelli di C4b saranno `…-c4b-…`. Costo accettato dall'utente: una sessione di scrittura, una d'esecuzione e un merge in più, circa il 20-30% di abbonamento in più; nessuna spesa in denaro.
2. **Forma del token: classico, con il solo scope `project`** (piano principale, decisione 3). I token a grana fine non danno i Projects di un utente (fatto). Il token delle bacheche serve solo alle chiamate GraphQL dei Projects (`client = "board"`); issue, sotto-issue, dipendenze, assegnazioni, commenti, conteggi e il login degli autori (`viewer` dell'agente) passano dal `gh` già autenticato dell'agente (`client = "agent"`). Il client di ogni documento e di ogni chiamata REST sta in `ghqueries.CLIENT`. Se la sonda mostra che il solo `project` non basta ad aggiungere a una bacheca un'issue di un repo privato: fermata `scope repo` («La sonda»). Costo: due credenziali da tenere in vita; un'operazione sul client sbagliato fallisce con `auth` o `rejected` (test `test_ops_use_declared_client`).
3. **Dove sta il token (utente, 25/11/2026: file protetto).** `~/.config/tollgate/board-token` (`boardtoken.default_token_path()`), cartella 0700, file 0600. Percorso fisso come la cartella di stato (`paths.default_state_root` ignora `XDG_*`), così una variabile dell'ambiente del modello non lo sposta (cambio rispetto alla proposta del controller con `XDG_CONFIG_HOME`). Mai nella cartella di stato: le evidenze degli eval ne contengono copie (C1, Task 8). **In modo di test** (sentinella) `token_path(state)` è `TOLLGATE_BOARD_TOKEN_FILE` (nuova in `TEST_ENVS`; il file si chiama sempre `board-token`), altrimenti `None`; vale `None` anche una variabile che nella forma lessicale (`os.path.abspath`) o in quella risolta (`Path.resolve()`) coincide con il percorso vero (il confronto lo fa `boardtoken` da sé: `path_forms` sta in `tollgate_checks`, che il nucleo non importa). Con `None` il token è `absent`, `write` e `remove` sollevano `TokenPathError`: la suite, che gira con la `HOME` vera, non tocca mai il token dell'utente. `boardtoken.status` guarda solo `lstat`, mai il contenuto: rifiuta un link simbolico, un file non regolare, di un altro utente o con permessi oltre 0600, e una cartella che è un link, non è una cartella, è di un altro utente o è scrivibile da gruppo o altri: stato `unsafe` con il motivo (`symlink`, `not_file`, `owner`, `mode`, `dir`, `dir_mode`). `read` apre con `O_RDONLY|O_NOFOLLOW` e ricontrolla tipo, proprietario e permessi con `fstat` sul descrittore (tra `status` e l'apertura il file può cambiare). Costo: un utente che tiene i segreti altrove deve usare questo percorso; con `HOME` condivisa tra macchine (raro) il token è lo stesso; ogni test che usa il token deve dare la variabile.

7. **Il token nel processo e la redazione.** `ghcli.Secret` (`__slots__`, `repr` e `str` danno `Secret(***)`, `reveal()` solo per l'ambiente del figlio). 8. **Errori di `gh`.** `ghcli.call(state, args, *, token=None, timeout=GH_TIMEOUT_S) -> Reply` fa **una sola prova**, sempre con `--include`, con `cwd = state.root`, e non solleva per un errore HTTP. `Reply(status, headers, data, errors, error_class, retry_after_s)`. `classify` in quest'ordine: uscita 0, stato < 400 e nessun `errors` → `None`; stato 403 o 429 con `retry-after` o `x-ratelimit-remaining: 0`, oppure 200 con `errors` e `x-ratelimit-remaining: 0`, oppure un errore che contiene `secondary rate limit` → `rate_limit`; stato 401, uscita 4, un 403 in cui **nessuno** degli scope di `x-accepted-oauth-scopes` (elenco separato da virgole) è tra quelli di `x-oauth-scopes`, oppure un errore GraphQL di scope insufficiente (il `type` lo registra S4; fino ad allora `fakegh` usa la forma che S4 deve confermare) → `auth`, così un token con lo scope sbagliato ferma la coda subito; **`rejected` solo da una lista chiusa**: stato in `REJECTED_STATUS = (400, 404, 410, 422)`, oppure 200 con `errors` tutti di un `type` in `REJECTED_GRAPHQL_TYPES` (vuoto nel Task 1; lo riempie il Task 5 con i `type` che S15 registra per un id inesistente e un input non valido); **tutto il resto è `transient`**: ogni 5xx, ogni uscita senza stato HTTP (rete assente, DNS, TLS, proxy, timeout, `gh` mancante), ogni stato o forma sconosciuti (progetto 8: «se GitHub non risponde, dà un errore 500 o la rete manca, la voce resta in coda e riparte dopo»). `retry_after_s` = `retry-after`, altrimenti `x-ratelimit-reset` meno l'ora, altrimenti 60, mai sotto `RATE_LIMIT_MIN_S = 60`. Le funzioni esistenti (`run_json`, `api`) non cambiano comportamento, salvo il messaggio di timeout di `run`, che cita il `timeout` dato e non `GH_TIMEOUT_S`. **Correzione del giro 2:** prima «il resto» era `rejected`, e senza rete ogni voce si abbandonava in circa 6 minuti. Costo: un errore definitivo in una forma che la lista non conosce tiene ferma la voce di testa del suo gruppo fino a `MAX_ATTEMPTS` (circa 2 giorni e 8 ore) invece di 3 tentativi; la sonda (S4, S15) e il Task 5 allineano le forme.

11. **La coda: tabella `gh_queue`, migrazione 8.** Non si riusa `intents` (ciclo di vita legato a un lavoro e agli atti; costo di riusarla: stati e chiavi da piegare). 13. **Attesa crescente e abbandono.** `ghqueue.RETRY_DELAYS_S = (60, 300, 1800, 7200, 21600, 86400)` (l'ultimo vale per ogni tentativo dopo il sesto), `ghqueue.MAX_ATTEMPTS = 8`, `ghqueue.MAX_REJECTED = 3`. Le attese sommano circa 2 giorni e 8 ore di macchina accesa (**correzione del conto del controller**, che diceva 3 giorni e mezzo: sette attese, 203.760 s); un tentativo conta solo quando gira davvero. All'ottavo fallimento, o al terzo se l'ultimo è `rejected` (un 422 certo non tiene fermo il suo gruppo per due giorni), la voce diventa `abandoned`, nasce `sync` con `outcome = "abandoned"`, la fotografia la conta, l'avvio di sessione lo dice in una riga, `board retry` la rimette in attesa. Una voce che non trova la cosa da cui dipende (un campo che la voce `field` non ha ancora creato) fallisce come `transient`. Costo: un guasto lungo di GitHub con la macchina sempre accesa fa abbandonare voci che poi vanno rimesse a mano; un `rejected` dato per sbaglio abbandona dopo circa 6 minuti.
14. **Limiti di frequenza e accesso negato: il blocco.** Il blocco sta in `meta`, chiave `ghqueue.BLOCK_KEY = "gh_block"`, valore JSON `{"reason": "rate_limit"|"auth"|"auth_agent", "until": <ISO>|null, "strikes": <n>}`; lo leggono e lo scrivono solo `ghqueue.block`, `set_block` e `clear_block` (Task 7), usati da `summary`, da `ghdrain` e dai comandi del token (nessun import da `ghqueue` a `ghdrain`). `rate_limit` ferma tutto lo svuotamento fino a `until` = ora + `max(retry_after_s, RATE_LIMIT_MIN_S * 2 ** (strikes - 1))`, al più `RATE_LIMIT_MAX_S = 3600`, senza contare un tentativo (senza intestazioni: 60, 120, 240 s; con `retry-after: 120`: 120, 120, 240 s); un successo azzera `strikes`. La classe `auth` dà il blocco `auth` su una chiamata del client `board` (il token delle bacheche) e `auth_agent` su una del client `agent` (il `gh` dell'agente non è autenticato): fermano tutto senza scadenza e senza contare tentativi; `auth` lo tolgono `board token set`, `board token remove` e un `board sync` che riesce, `auth_agent` solo un `board sync` che riesce (dopo `gh auth login`). Costo: un `auth` dato per sbaglio da GitHub ferma la coda finché l'utente non lancia `board sync`.
15. **Le scritture non idempotenti** (tabella «Le scritture verso GitHub»): si ripetono senza controllo solo le operazioni che GitHub rende idempotenti o che impostano uno stato; le creazioni si **ricontrollano prima**, cercando un marcatore stabile e non delicato, `ghops.marker(kind, key) = "<!-- tollgate:" + kind + ":" + sha256(key)[:16] + " -->"`, aggiunto dall'operazione in fondo al corpo dopo la normalizzazione (un testo dell'utente che passa dal filtro non può imitarlo: `defuse`); sotto-issue, dipendenze e assegnazioni si leggono prima. Ogni lista letta prima di una creazione si legge **per intero**, con `per_page=100` e il parametro `page` fino a una pagina con meno di 100 elementi (`comments_list`, `sub_issues_list`, `blocked_by_list`: `call` usa `--include`, che non si combina con `--paginate`); `issues_recent` legge una pagina, le ultime 100 per data di creazione (S22). Un'issue, un commento o una scheda bozza col marcatore si adotta **solo se l'autore** (`user.login` per REST, `creator.login` per una bozza) è il login del client che scrive, letto con `viewer` e tenuto in `Clients.cache`, come fa `bot_comment` del gate: in un repo pubblico chiunque può scrivere un marcatore prevedibile. Ogni operazione comincia sempre dal controllo, quindi dopo un 500 a corpo vuoto il tentativo successivo riparte da lì. Costo: una lettura in più per ogni creazione e una per svuotamento (`viewer`); una creazione riuscita che GitHub non mostra ancora nella lettura (S22) darebbe un doppione; se l'utente cambia l'account del `gh` dell'agente tra la creazione e il controllo nasce un doppione.
16. **Payload per nomi, non per id.** Un payload nomina il progetto per titolo, il campo per nome, l'issue per numero: l'operazione trova gli id con le letture, che `ghops.Clients.cache` tiene per la durata di uno svuotamento. `field`, `item`, `draft` e `field_value` trovano o creano il Project dal titolo (`find_or_create_project`), così non aspettano una voce `project` di un altro gruppo. Così una voce non dipende dall'esito di un'altra voce, salvo il campo di `field_value` (decisione 13). Costo: qualche lettura GraphQL in più per svuotamento (1 punto ciascuna).
17. **Quando si svuota: mai in linea.** Hook e comandi mettono solo in coda (SQLite locale). `ghdrain.kick(conn, state, *, now) -> bool` avvia lo svuotamento staccato se il token è `present`, esiste una voce `pending` scaduta, nessun blocco è attivo e il timbro `board-drain.stamp` ha più di `KICK_INTERVAL_S = 30` s; in modo di test solo con `TOLLGATE_BOARD_KICK=1`. L'avvio è un doppio `fork` (il primo figlio fa `setsid`, rifà `fork` ed esce con `os._exit(0)`, mai `sys.exit`, che rieseguirebbe la chiusura di `unittest` e della connessione; il nipote chiude i descrittori da 3 in su, mette 0-2 su `/dev/null` ed esegue `sys.executable -B <bin/tollgate> board drain`, lo stesso Python ≥ 3.11 scelto dal wrapper; il padre fa `waitpid` del primo figlio): nessun oggetto `Popen` vivo, nessun zombie, nessun `ResourceWarning`. **Un solo aggancio:** la fine di `run_hook` (parametro nuovo `kick: bool = False`, che `cli` passa vero per `hook`), nel `finally` dopo `signal.alarm(0)` e prima di `conn.close()`; vale per ogni hook di un repo attivo, compreso il `PostToolUse` di Bash dopo un comando del modello, e SessionStart. `cli.main` non chiama `kick`: un comando Bash del modello può girare nella sandbox di Claude Code, dove un processo staccato può morire o restare senza rete. Che gli hook girino fuori dalla sandbox e che Claude Code lasci vivere i discendenti di un hook è **da verificare**: VE2 (spec del nucleo) lo mostra solo in una corsa di `claude plugin eval` e lo scan pre-flight prova `hooks/run` da solo; lo dirà il primo uso vero (C4b, C6), e se non regge lo svuotamento parte solo con `board sync`. `kick` non solleva mai. Lo svuotatore prende `board-drain.lock` con `flock(LOCK_EX | LOCK_NB)`: chi non lo prende esce con 0, chi lo prende scrive il suo PID nel file (i test lo leggono per fermarlo); non tiene una transazione aperta durante una chiamata a `gh`. Budget `DRAIN_BUDGET_S = 120` in background, `SYNC_BUDGET_S = 600` per `board sync`; timeout per chiamata `CALL_TIMEOUT_S = 20`; almeno `WRITE_GAP_S = 1.0` tra due scritture; non comincia una voce se restano meno di `CALL_TIMEOUT_S` secondi. Un errore inatteso dello svuotatore va in `<stato>/board-errors.log` (tipo dell'eccezione e messaggio redatto). Lo scan pre-flight verifica, senza rete, che un nipote avviato da un hook sopravviva a `hooks/run` e che il wrapper non lo aspetti. Costo: una scrittura appena messa in coda parte entro 30 s, al hook successivo; un comando lanciato dall'utente nel suo terminale non avvia lo svuotamento (parte al primo hook o con `board sync`); `board sync` o `board drain` lanciati dal modello nella sandbox senza rete costano un tentativo `transient` per voce (pagina d'uso).
18. **L'evento `sync`** (piano principale, decisione 2): tipo nuovo, busta `v` 1. `data`: `item` (l'`id` della voce in `gh_queue`), `kind`, `outcome` (`done`, `retry`, `abandoned`, `skipped`), `attempts`, `error_class`, `reason` per `skipped` (`local_remote`, `forbidden`), `problems` per `forbidden` (lista di `{"field": <nome del campo>, "code": <codice>}`, mai il valore); C4b aggiungerà `differences`. 19. **Il filtro di ciò che esce** (progetto 7; anti-obiettivo). `tollgate_analysis.outbound`: `KINDS` (Task 7), `normalize(kind, payload)` (applica `prbody.defuse` a `title`, `titles` e `text`; gira **una volta sola**, in `submit`, perché `defuse` non è idempotente) e `check(kind, payload, forbidden) -> list[Problem]` (Task 8). ## Costo e tempi dell'esecuzione

Stime larghe (lezione di C2). Nessuna spesa in denaro: niente `claude -p`, niente eval; GitHub è gratis per un repo privato e i Projects di un account personale. Il consumo è quota dell'abbonamento: circa 30-45 subagenti (implementatori e correzioni su opus, revisori, scan e revisione finale su Fable), simile a C2 senza la prova reale. Tempo: una corsa della suite dura 1,5-2,5 ore; dieci task con codice, i giri di correzione e tre corse finali fanno circa 15-22 corse, cioè 3-6 giorni di calendario in una sessione d'esecuzione, più le fermate (`sonda` con la preparazione dell'utente, circa 15 minuti suoi; eventuali `scope repo`, `sotto-issue`, `fatto diverso`; merge; worktree).
