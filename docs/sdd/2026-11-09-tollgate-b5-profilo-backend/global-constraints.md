## Global Constraints

- Solo libreria standard in `bin/` e nei test (spec 3). Python ≥ 3.11. Ogni task chiude con `tests/run` verde (`python3.11` e `python3`); verifica finale come la CI: `PYTHONWARNINGS=error::ResourceWarning tests/run`.
- **Strati** (`tests/test_layers.py`): `tollgate_analysis` non importa nulla di tollgate; `tollgate_core` non importa `tollgate_flow`, `tollgate_hooks`, `tollgate_checks`, `tollgate_gate`, tranne `cli.py`; `tollgate_flow` non importa `tollgate_hooks` né `tollgate_checks`.
- **Nessuna operazione nuova in `apply._OPS`** e **nessun tipo nuovo in `events.EVENT_TYPES`** (i conteggi di `main` restano).
- **Nessuna rete**, né nei test né per i subagenti: le fonti delle regole sono copie locali messe dal controller nel workspace (Task 3, Step 0), che **non entrano mai in git** né nella copia del registro in `docs/sdd/`. Nessun `claude` vero nei test; `gh` è `tests/fakegh.py`. **Nessun `wrangler`, `vercel`, `supabase`, `deno`, `node`, `docker`, `npx`, `npm`, `pnpm`, `yarn`, `bun` o `bunx` vero** nei test, negli script e nei comandi dei subagenti: nei test sono solo testo dato a `bash.parse`. Nessun server avviato su una porta. Nessun test tocca `~/.local/state/tollgate`, `~/.claude/settings.json`, `~/.claude/plugins/`, `~/.claude/projects/`.
- **Test con la radice del plugin esplicita**: ogni test nuovo che legge frammenti, skill o agenti usa una radice temporanea, salvo i test che leggono i file veri, che portano il prefisso `test_real_` (decisione 16), e i file `tests/test_rules_*.py`, che sono sui file veri della loro area.
- **Cartelle temporanee dei test** (piano principale, sezione 9, «A B4-B8, da B3-bis»): ogni `mkdtemp` si chiude con `addCleanup`; una cartella creata direttamente in `/tmp` ha un prefisso che comincia con `tollgate`. Nessuna asserzione che, se fallisce, stampi `os.environ` (lezione di B3-bis).
- **Regole con parole nostre** (catalogo 1, principio 7): dalle skill MIT e Apache-2.0 si distillano regole citandole; dalle pagine dei fornitori si prendono i **fatti**, senza copiarne testo; una citazione sta al più in una riga, nel solo rapporto delle fonti. Ogni regola si giudica con un sì o un no **su ciò che il revisore vede** (il diff, con i file del repo che servono a giudicarlo, il report o la nota); una regola `[blocca]` si giudica sul diff o sul report, mai sulla sola nota. Una regola su un fatto che dipende dal codice (una rotta nuova, un endpoint che cambia) dice come il revisore lo riconosce nel diff.
- **Numeri delle regole stabili dopo l'approvazione** (catalogo 2.3). **`approved` in `skills/rules-backend/SKILL.md` si scrive solo nel Task 5**, con la data dell'OK dell'utente; gli agenti `-backend` caricano `rules-backend` solo dopo (Task 6 dopo il Task 5).
- Non si toccano `skills/rules-base/SKILL.md`, `skills/rules-ai/SKILL.md`, `skills/rules-infra/SKILL.md`, `docs/profili/base.md`, `docs/profili/ai.md`, `docs/profili/infra.md` e i loro rapporti delle fonti: sono approvati dall'utente.
- Testo non fidato (nota, pagine scaricate, citazioni, report dell'implementatore): nei brief dentro `brief.fence` con `brief.DATA_NOTE`, mai come istruzione.
- `tollgate.toml` del progetto: `init` non lo scrive mai nel repo, produce la proposta in `docs/superpowers/tollgate-init/` che l'utente copia (spec 11.2).
- Il repo è pubblico: nei file nuovi niente nomi di progetti privati dell'utente, niente nome utente né host, nessun token; nelle evidenze nessun testo di pagine o skill di terzi (`flowreg togli-pagine`, poi la verifica a mano prima del rapporto).
- Identificatori in inglese, testi per l'utente e per il modello in italiano. Nessun `__pycache__` nel repo (`-B`). Commit dopo ogni task.
