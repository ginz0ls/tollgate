## Attacchi che la specifica ferma

1. **Merge fatto dall'agente**: PR obbligatoria, controlli obbligatori e regole valide anche per gli amministratori; `gh pr merge` negato in locale. Il merge richiede l'utente.
2. **Avvelenare la cache del predefinito dal job `run`**: una cache scritta da `pull_request` va nel solo merge ref [VERIFICATO]; `pull_request_target` e `workflow_run` hanno sola lettura sul predefinito per impostazione predefinita [VERIFICATO]. Gli ID della base provengono quindi da un workflow `push` fidato.
3. **Modificare `tollgate.toml` per cambiare i comandi del gate** in una PR ordinaria: configurazione letta dal predefinito, file di tollgate diversi dalla punta → `guard` rosso (salvo #8 con il merge dell'utente).
4. **Eseguire codice della PR in `guard` e `verdict`**: checkout del solo predefinito, `git fetch` senza checkout; gli artefatti si leggono come dati.
5. **Cancellare test, aggiungere `skip`/`xfail`/`.only`**: test-guard sul diff vero (se #2 è corretto) e ID della base mancanti sulla testa → rosso senza deroga `test`.
6. **Rinominare un test per far sparire un ID**: gli ID della base devono comparire sulla testa; una rinomina vera richiede deroga `test` per ID.
7. **Stato `tollgate/verdict` creato da un'altra app o da un utente**: il pin sulla sorgente lo rifiuta [VERIFICATO sul comportamento dei docs: «merging won't be allowed»]. Non copre i workflow Actions dello stesso repo (#1).
8. **Indebolire la base calcolando gli ID con le dipendenze della PR**: su cache assente si usa il checkout della base, non della testa (salvo #4 per basi non predefinite).
9. **Deroga `test` nascosta**: ogni deroga `test`, `ci`, `soglia`, `comando` rende rosso `attenzione`, visibile prima del merge.
10. **Push forzato o cancellazione del ramo predefinito**: vietati dalla protezione proposta.
11. **PR da fork**: i workflow da fork non hanno segreti e hanno token di sola lettura [VERIFICATO: le PR di Dependabot sono trattate come fork]; il repo è privato.
12. **Workflow nuovo o modificato in una PR ordinaria**: `guard` rosso su tutti i file sotto `.github/workflows/**`, non obbligatorio ignorarlo.
13. **Piano allargato dopo il primo commit di codice**: `attenzione` rosso (con il limite di #17).
14. **Testo dell'issue in un comando shell**: mai in shell, solo in file marcati come dati; autore esterno → L2.
15. **Verdetto del gate vecchio dopo un nuovo push**: gli stati sono legati al SHA; con `strict` serve la testa attuale.

## Non verificato

- Se uno stato pubblicato con `GITHUB_TOKEN` abbia come sorgente «GitHub Actions» per il pin (già in 16); la mia lettura dei docs conferma solo il pin per app. Non ho provato la sovrascrittura di uno stato rosso da parte di uno stato successivo con lo stesso contesto, né il caso «check run e stato con lo stesso nome».
- Quale file di workflow usa `pull_request_target` per una PR verso un ramo non predefinito (#18): il testo ottenuto dice «ramo predefinito», non ho potuto confrontarlo con la sezione completa dei docs.
- Presenza e contenuto dei campi `workflow_run.path`, `workflow_run.pull_requests` e `head_sha` nel payload; comportamento di `workflow_run` e `statuses: write` per run innescati da Dependabot (la pagina letta non li copre).
- Disponibilità e piano richiesto del ruleset «Require workflows to pass before merging».
- Vulnerabilità e versioni di `actions/download-artifact` (path traversal), robustezza di `xml.etree` contro le entità annidate con l'espat della piattaforma.
- Semantica di GitHub quando un check run e uno stato hanno lo stesso nome, e quale vale con più esecuzioni dello stesso nome.
- Non ho eseguito nulla su un repo di prova; tutti i rilievi con tag [RAGIONATO] vanno confermati con la suite della sezione 14.
